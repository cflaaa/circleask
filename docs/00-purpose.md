# 00 · 这个工程为什么存在

## 用户是谁

拿着一本教材或一份资料、看不懂某一段、又不想把整页丢给搜索引擎的人。

## 要解决的问题

学习时卡住的地方往往很小：一个公式的某一步、一张图的某个标注。
现有的做法都不顺手——

| 做法 | 卡在哪 |
|---|---|
| 复制文字去搜 | 扫描版 PDF 没有文字层，复制不了 |
| 整页截图去问 | 模型被无关信息淹没，答得泛 |
| 手动打字描述 | 「就是那个带箭头的部分」说不清 |

## 我们的做法

**让用户用手指圈出来。** 圈选区域就是问题本身，不需要语言描述。

链路是：导入 PDF → 渲染成图片 → 圈一块 → 把那块图片连同上下文交给视觉模型 → 流式回答。

## 不做什么

明确划掉的东西，避免工程膨胀：

- **不做题库/刷题。** 只做「看不懂就问」。
- **不做笔记编辑器。** 标记只留痕，不提供富文本。
- **不做云端同步（这一版）。** 数据全在本机，隐私优先。
- **不做 PDF 编辑器。** 只读。

## 成功的标准

不是功能多少，是这三条：

1. 老平板上翻 200 页的扫描版教材**不卡、不崩**。
2. 圈完松手到看见第一个字，**两秒以内**。
3. 换一种屏幕（手机→平板→桌面），**功能代码一行不改**。

## 为什么这次另起工程

旧工程是一路长出来的，功能与界面缠在一起（单文件 3500 行、165 处 DOM 引用）。
后来虽然拆了目录，但**拆分是事后切的，边界是猜的**。

这次反过来：**先定边界，再写代码**。所以第一版代码量很小，
但每一层的职责写在文件头，`npm run check` 会强制检查有没有越界。
