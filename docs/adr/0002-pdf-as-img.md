# ADR 0002 · PDF 页面渲染成 `<img>`，而不是长期挂着 `<canvas>`

- 日期：2026-11-02
- 状态：已采纳

## 背景

旧实现是每页一个 `<canvas>`，翻页时创建、离屏时回收。
问题在于 canvas 是**昂贵且不可缓存**的：

- 一张 2000×2800 的 canvas 常驻显存约 22MB（4 字节/像素），
  同时挂 5 页就是 110MB，老机型直接触发系统回收，白屏。
- canvas 的内容不能被浏览器当作图片缓存，缩放时要么重绘要么发虚。
- 每页都要跑一遍 pdf.js 的绘制管线，翻页有明显的空档。

## 决定

渲染管线改成：

```
pdf.js → 离屏 canvas（临时） → toBlob() → ObjectURL → <img> → 立刻丢弃 canvas
```

DOM 里只留 `<img>`，canvas 只在渲染的那一瞬间存在。

## 为什么这样更快

| 维度 | canvas 常驻 | img + Blob URL |
|---|---|---|
| 内存 | 解码后的位图常驻，约 22MB/页 | 编码后的 JPEG/WebP，约 200~400KB/页 |
| 缩放 | 重绘或发虚 | 浏览器自己做高质量缩放 |
| 合成 | 每帧参与合成 | 走图片快路径，GPU 直接贴 |
| 缓存 | 无 | 可被 HTTP/内存缓存复用 |

数量级差别：同样 5 页，**110MB → 1.5MB**。

## 代价与对策

1. **Blob URL 必须手动释放**，否则内存只增不减。
   → `adapters/render/pdfjs-img-renderer.js` 里做 LRU，只保留最近 N 页的 URL，
   超出的 `URL.revokeObjectURL()`。
2. **`toBlob` 是异步的**，渲染接口因此返回 Promise。
   → 端口签名本来就设计成异步，core 侧无感。
3. **高倍缩放会糊**，因为图片有固定像素尺寸。
   → 按目标显示宽度 × devicePixelRatio 渲染（圈选用 1600px 目标宽度重渲染一次），
   而不是拿屏幕截图。

## 什么情况下该推翻它

如果将来要做「页内文字选中」，img 没有文字层。
那时的解法是**并行挂一层透明的文字层**（pdf.js 的 text layer），
而不是退回 canvas。
